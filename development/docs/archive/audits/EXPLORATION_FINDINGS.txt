WHAT IS THIS PROJECT?
================================================================================

KneeSpa Medical Device Control System - A therapeutic knee rehabilitation 
apparatus controller that runs on a Raspberry Pi and manages:

  - 3 motorized actuators (compression, rotation, lateral flexion)
  - Pressure application monitoring (load cell sensor)
  - Pre-programmed treatment protocols (AC1-AC4 configurations)
  - Patient authentication and profile management
  - Real-time treatment progress displays

The system is designed to be used in clinical/medical facilities for knee 
rehabilitation therapy with safety-critical controls and compliance features.

================================================================================
KEY COMPONENTS (11 MAJOR MODULES)
================================================================================

1. MAIN APPLICATION (main/kneespa.py)
   - Central orchestrator for UI, protocols, and hardware
   - 2,259 lines of PyQt5 code
   - Handles user authentication, patient selection, protocol execution
   - Manages real-time status displays and emergency stop

2. PROTOCOL EXECUTOR (main/helpers/protocols.py)
   - Multi-stage treatment sequence runner
   - Manages pressure ramps, actuator positioning, duration limits
   - Supports pulsing mode for therapeutic effect
   - Runs in worker thread for non-blocking execution

3. ARDUINO INTERFACE (main/helpers/arduino.py)
   - Serial communication with Arduino via /dev/serial0
   - Sends movement and pressure commands
   - Parses real-time status updates (positions, pressure)
   - Implements connection retry logic and rate limiting

4. CONFIGURATION MANAGER (main/config/config.py)
   - Loads INI-format configuration file
   - Manages calibration factors and actuator position mappings
   - Provides type-safe access to settings

5. CONSTANT DEFINITIONS (main/config/constants.py)
   - Hardware limits (pressure, angles, distances)
   - Actuator IDs and command prefixes
   - Arduino communication settings
   - UI page definitions
   - Safety thresholds

6. RESET WORKER (main/helpers/reset_worker.py)
   - Multi-step hardware initialization sequence
   - Runs asynchronously to prevent UI blocking
   - Implements retry logic with DTR-based Arduino reset
   - 6-step reset process: Y → L5 → I14 → A13 → I12 → L0

7. CSV HELPER (main/helpers/csv.py)
   - Loads user authentication data from CSV
   - Loads patient records
   - Provides PIN-based user lookup

8. LOGGING FRAMEWORK (main/helpers/logging.py)
   - Singleton logger for application-wide logging
   - Rotating file handlers for main, error, debug logs
   - Component-based context tagging
   - Qt warning filtering

9. PRESSURE DIALOG (main/ui/dialogs/pressure_dialog.py)
   - Floating dialog showing current pressure
   - Color-coded: Green (<50), Orange (50-70), Red (>70) lbs
   - Updates when pressure changes > 0.5 lbs
   - Always-on-top window during protocol execution

10. TIMER DIALOG (main/ui/dialogs/timer_dialog.py)
    - Countdown timer for protocol duration
    - Color-coded by remaining time
    - Syncs with main window protocol state
    - Displays HH:MM format

11. ARDUINO FIRMWARE (main/motor/motor.ino)
    - 889 lines of C code for Arduino Uno
    - Controls 3 motor drivers via I2C (IDs: 12, 13, 14)
    - Reads HX711 load cell for pressure measurement
    - Reports status periodically or on-demand
    - Handles emergency stop, jerking motion, calibration

================================================================================
HOW IT WORKS: TYPICAL PATIENT TREATMENT
================================================================================

1. User logs in with PIN code
2. Patient is selected from database
3. Treatment protocol is chosen (AC1, AC2, AC3, or AC4)
4. User configures parameters (pressure target, angles, duration)
5. Hardware is reset (actuators to neutral, sensors zeroed)
6. User clicks START
   - Pressure dialog opens showing current load
   - Timer dialog shows countdown
   - Protocol runs in background worker thread
7. Treatment stages execute:
   - Position actuators to starting angles
   - Gradually increase pressure in 10 lbs increments
   - Apply lateral flexion patterns (left/right movements)
   - Maintain pressure and motion for specified duration
8. Treatment completes:
   - Pressure released to zero
   - Actuators return to neutral
   - Session logged
   - Summary displayed

================================================================================
HARDWARE CONTROL CHAIN
================================================================================

PyQt5 UI (Main Thread)
        ↓ Signals
Worker Thread (Protocols)
        ↓ Serial Commands
Arduino Interface (arduino.py)
        ↓ Serial Port (/dev/serial0, 115200 baud)
Arduino Uno Microcontroller
        ↓
    I2C Motors (3 controllers: 12, 13, 14)
        ├─ Actuator A12 (Axial): 0-4 inches
        ├─ Actuator B13 (Horizontal): -25 to 5 degrees
        └─ Actuator C14 (Lateral): -20 to 20 degrees
    
    HX711 Load Cell (Pressure sensor)
        └─ Measures force in pounds (0-80 lbs safe)
    
    GPIO Controls
        ├─ Pin 3: Emergency stop input
        ├─ Pins 4, 5: External actuator direction
        └─ Pin 9: External actuator PWM speed

================================================================================
COMMAND AND STATUS COMMUNICATION
================================================================================

Commands sent TO Arduino (Serial1, 115200 baud):
  A12<inches>    - Position axial actuator (e.g., A122.5)
  K<position>    - Set lateral position (e.g., K1500)
  B<position>    - Set horizontal position (e.g., B500)
  P<pressure>    - Set target pressure (e.g., P60)
  L5<A><B>       - Set zero marks (e.g., L51602080)
  J              - Start jerk motion
  JS             - Stop jerk motion
  X              - Emergency stop
  Y<code>        - Reset command (e.g., Y12)
  S              - Request status
  HF1/HF0        - Enable/disable high-frequency updates
  L0<factor>     - Set calibration factor

Status received FROM Arduino:
  STATUS_START|S|<posA>|<posB>|<posC>|<pressure>|STATUS_END
  Example: STATUS_START|S|500|800|0|45.3|STATUS_END

  DONE           - Command completed
  OK             - Test response

================================================================================
SAFETY AND CONSTRAINTS
================================================================================

Hardware Limits (Enforced):
  - Axial Position: 0 to 4 inches
  - Horizontal Position: -25 to 5 degrees
  - Lateral Position: -20 to 20 degrees
  - Pressure: 0 to 80 lbs (absolute maximum for safety)

Software Safety Features:
  - All position commands bounded to hardware limits
  - Pressure capped at 80 lbs maximum
  - Emergency stop via GPIO pin 16 (immediate shutdown)
  - Command rate limiting (minimum 200ms between commands)
  - Connection verification with periodic test commands
  - Timeout protection (30-second timeout on connections)
  - Serial buffer monitoring (warns at 80% full)
  - Pressure tolerance checking (allowing ±3 lbs variation)

Medical Compliance Features:
  - PIN-based user authentication
  - Patient identification required for all treatments
  - Treatment session logging with timestamps
  - Comprehensive error logging for audit trails
  - Video instruction playback for safe operation
  - Calibration tracking and validation

================================================================================
KNOWN ISSUES AND RISKS
================================================================================

CRITICAL ISSUES:
1. Unsynchronized I2Cstatus flag - Race condition in reset operations
2. Protocol parameters can be modified during execution - Inconsistent behavior
3. TOCTOU (Time-Of-Check-Time-Of-Use) in serial communication
4. Missing PyQt signal definition (display_weight_emit)
5. No mutex protection on shared resources

IMPACT: Patient safety risk - medical device with unprotected concurrency

RISK FACTORS:
- Multiple threads access shared state without synchronization
- Continuous background I/O thread reading from Arduino
- UI thread can modify protocol parameters during execution
- Reset operations depend on unreliable flag synchronization
- Serial port access can fail if connection state becomes inconsistent
